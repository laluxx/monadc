[DEC id:dec.memory.automatic-source-language-2026-07-29 src:user-request conf:high]
  Ordinary Monad source does not expose =free=, =drop=, =copy=, ownership
  qualifiers, lifetime syntax, or borrow annotations. The compiler infers
  resource behavior and elaborates source into an explicitly resource-safe
  internal language.

[DEC id:dec.memory.before-embedding-abi-2026-07-29 src:user-request conf:high]
  Stabilize memory and resource semantics before freezing the embedding ABI.
  The C API must reflect proven ownership, escape, and lifetime rules rather
  than becoming an accidental second memory model.

[OBS id:obs.memory.baker-linear-lisp-2026-07-29 src:etc/pdfs/BakerLinearLisp.pdf conf:high]
  Baker's strictly linear machine conserves unity accessibility: visible heap
  structures are trees without sharing or cycles, every binding is consumed,
  and FREE recursively returns an unused tree to the free list. Its faster
  virtual-heap design permits hidden sharing through hash consing and reference
  counts. Therefore compile-time placement of frees is sufficient for the
  strictly linear fragment, while dynamic sharing requires either restriction,
  copying, regions, or runtime ownership bookkeeping.

[DEC id:dec.memory.quantities-2026-07-29 src:context/memory.org conf:high]
  Use the exact usage semiring =N ∪ {ω}=, retaining symbolic quantity
  expressions and constraints until solving:
  - =0=: erased or not consumed at runtime;
  - =1=: consumed exactly once;
  - finite =n=: consumed exactly =n= times;
  - =ω=: unbounded or conservatively unknown usage.
  Quantities belong to internal binders and arrows, not nominal value types.
  The familiar ={0,1,ω}= domain is a useful post-solve classification, not
  the inference representation. This follows the compositional direction of
  quantitative type theory and avoids duplicating every type into linear and
  unrestricted variants.

[DEC id:dec.memory.quantity-optimization-evidence-2026-07-29 src:user-request conf:high]
  Preserve exact finite quantities as optimization evidence. Zero permits
  erasure when effects also permit it; one enables moves and rules out useful
  result memoization; larger finite counts inform duplication, sharing, reuse,
  and cost-based memoization. Usage alone does not authorize memoization:
  purity, termination/exception behavior, memory cost, and recomputation cost
  remain separate proof obligations.

[OBS id:obs.memory.static-count-boundary-2026-07-29 src:context/memory.org conf:high]
  Exact source occurrence counts are not always exact dynamic reference
  counts. Branches are path-sensitive, loop multiplicities may be symbolic or
  data-dependent, closures can escape, and foreign code can retain values.
  The solver keeps exact and symbolic quantities where provable and widens to
  =ω= only at an honest static boundary; ownership insertion additionally
  requires alias, escape, and effect information.

[DEC id:dec.memory.elaboration-2026-07-29 src:context/memory.org conf:high]
  Surface inference produces type, effect, escape, and usage constraints.
  Solving elaborates typed AST into a Resource IR with explicit operations:
  =move=, =borrow=, =dup=, =drop=, =reuse=, =alloc-region=, and
  =end-region=. These operations are compiler artifacts and are erased or
  lowered before LLVM emission.

[DEC id:dec.memory.representation-classes-2026-07-29 src:context/memory.org conf:high]
  Resource behavior is representation-sensitive:
  - immediate/unboxed values are freely duplicable and require no drop;
  - unique heap values move, borrow, destructure, reuse, or drop;
  - immutable shared values receive compiler-inserted precise dup/drop;
  - region values are reclaimed in bulk and cannot escape their region;
  - foreign values follow a registered C ownership contract.
  Linearity alone is not used as a synonym for heap allocation.

[DEC id:dec.memory.control-flow-accounting-2026-07-29 src:context/memory.org conf:high]
  Usage is path-sensitive. Every reachable branch must consume compatible
  resources; joins reconcile ownership with explicit Resource IR operations.
  Pattern matching consumes a scrutinee structurally, closures record captured
  quantities, exceptions/nonlocal exits carry cleanup edges, and loops require
  a resource invariant across the back edge.

[DEC id:dec.memory.safety-theorems-2026-07-29 src:context/memory.org conf:high]
  The Resource IR and checker must support proofs, mechanized if practical, of:
  1. preservation and progress for resource-typed terms;
  2. no use-after-move or use-after-free;
  3. no double drop;
  4. every owned allocation is dropped exactly once or returned/escaped under
     an explicit ownership contract;
  5. borrows do not outlive owners or regions;
  6. erasure/lowering preserves observable program behavior;
  7. inserted reuse is observationally equivalent to fresh allocation.

[DEC id:dec.memory.honest-boundary-2026-07-29 src:context/memory.org conf:high]
  Do not claim universal compile-time collection. Arbitrary cycles, opaque
  foreign retention, concurrency, and unrestricted dynamic graphs make static
  last-use undecidable in general. Monad either proves such programs safe,
  represents sharing with precise bookkeeping, confines it to a region, or
  rejects it with a source-located explanation.

[DEC id:dec.memory.two-calculi-2026-07-29 src:qtt_usage.h conf:high]
  Keep quantitative demand and operational ownership distinct. Graded/QTT
  judgments describe how a term depends on binders. A later linear resource
  calculus elaborates typed, explicit control flow into =dup=, =drop=, and
  =reuse=. Neither layer is allowed to silently substitute for the other.

[DEC id:dec.memory.symbolic-control-operators-2026-07-29 src:qtt_usage.c conf:high]
  Demand expressions retain control structure:
  - =add(p,q)= is sequential demand;
  - =choice(p,q)= is mutually exclusive path demand;
  - =capture(p)= records closure-environment retention separately from calls;
  - =repeat(p)= records data-dependent repeated demand.
  Only solved finite quantities participate directly in the
  =N ∪ {ω}= semiring. Control operators remain symbolic until control-flow,
  escape, and invocation constraints are solved.

[DEC id:dec.memory.layered-ir-2026-07-29 src:qtt/core.h conf:high]
  Monad uses several small IRs with distinct proof obligations, not one
  universal IR:

  joins. Resource IR alone introduces =move/borrow/dup/drop/reuse=. Erasing
  resource operations must recover an observationally equivalent Core term.

  MLIR can later host stable Monad dialects or optimization lowerings, but it
  does not supply the ownership calculus, inference rules, or reclamation
  proof. Re-evaluate it after Core and Resource IR interpreters, checkers, and
  erasure-equivalence tests are established.

[DEC id:dec.memory.resource-transition-system-2026-07-29 src:qtt/resource.c conf:high]
  Let =Γ= be a finite set of live owned capabilities qualified by
  =(ModuleId,BinderId)=. Resource instructions implement these partial
  transitions:
  - =alloc x=: =x ∉ Γ= and =Γ' = Γ ∪ {x}=;
  - =borrow x=: =x ∈ Γ= and =Γ' = Γ=;
  - =move x=: =x ∈ Γ= and =Γ' = Γ ∖ {x}=;
  - =drop x=: =x ∈ Γ= and =Γ' = Γ ∖ {x}=;
  - =branch(p,q)=: =Γ ⟶p Γ₁= and =Γ ⟶q Γ₂= require =Γ₁ = Γ₂=.
  A closed resource block is accepted only when its final context is empty.

[OBS id:obs.memory.resource-safety-induction-2026-07-29 src:qtt/resource.c conf:high]
  Induction over the verified instruction sequence establishes, for the
  abstract capability machine: a borrow never observes a consumed capability;
  every move/drop consumes one currently live capability; allocation cannot
  overwrite a live or previously consumed identity; and both conditional paths
  expose the same continuation context. The conservation equation is
  =inputs + allocs = moves + drops + live=. Acceptance sets =live = 0=, hence
  every abstract owned capability is consumed exactly once on every accepted
  path.

  =use_x(if c t e) = use_x(c) + choice(use_x(t), use_x(e))=

  Choice is not collapsed into addition: doing so would count mutually
  exclusive paths together and obscure branch-local last use. Exact subtree
  occurrences remain available to the ownership elaborator for each arm and
  continuation.
