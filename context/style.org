[OBS id:obs.style.hybrid-c-signature-lisp-body src:user-request conf:high]
  MonadC supports a hybrid style where the function head/signature reads closer
  to C-like parameter and return declarations, while the body remains Lisp-like
  S-expression code. Example shape:

#+BEGIN_SRC monad
(define (push-vertex [x :: F32] [y :: F32]
                     [u :: F32] [v :: F32]
                     [c :: Color])
  (unless (g-vertex-count >= MAX-VERTICES)
    (define [vtx -> Vertex]
      (g-vertices g-vertex-count))
    (set! vtx.x x)
    (set! vtx.y y)
    (set! vtx.u u)
    (set! vtx.v v)
    (set! vtx.r c.r)
    (set! vtx.g c.g)
    (set! vtx.b c.b)
    (set! vtx.a c.a)
    (set! g-vertex-count (g-vertex-count + 1))))
#+END_SRC

[THINK id:think.style.hybrid-c-lisp-use src:user-request conf:high]
  Human framing: this style is useful because the type/ABI surface looks
  concrete and C-adjacent, while the body keeps Lisp's uniform expression
  syntax. It is especially relevant for low-level graphics/runtime code where
  fields, scalar types, buffers, and mutation are prominent.

[DEC id:dec.style.two-blank-lines-between-functions-2026-07-16 date:2026-07-16 by:human src:user-request conf:high]
  Monad source uses exactly two blank lines between top-level function, method,
  class, instance, data, and value declarations. Apply this convention to files
  as they are touched; do not require an immediate repository-wide whitespace
  rewrite. Tests and declaration bodies remain compact according to their local
  structure.

[DEC id:dec.style.core-must-read-well-2026-08-04 date:2026-08-04 by:human src:user-request conf:high]
  Core Monad code must be visually excellent as well as semantically correct.
  Prefer small concepts with honest names, ordinary public combinators over
  =__rt_*= calls, vertically readable matches, and separate declarations over
  clever alignment of unrelated types. Do not expose compiler workarounds as
  public abstractions. Respect the reader's real continuation grammar: a
  beautiful layout that parses incorrectly is not valid style.

  The desired standard is majestic rather than merely tidy: a Core module
  should present a small number of visible conceptual movements, with calm
  whitespace and names that let the reader understand the design before the
  implementation details. Avoid undifferentiated helper walls and accidental
  vertical noise. When a module is a flagship example, retain mechanical
  source-shape coverage for its section structure, excessive blank runs, raw
  runtime escape hatches, and unreasonable line width.

[DEC id:dec.style.receiver-relative-guards-2026-07-28 date:2026-07-28 by:human src:user-request conf:high]
  Guards on a single matched subject use receiver-relative Wisp predicates.
  When a guarded definition has exactly one subject, place that subject and the
  first guard pipe on the same line; align continuation pipes beneath the first
  pipe. Omit the unary subject from receiver-relative comparisons. Compose
  predicates with readable infix =and= or =or=; do not encode these guards as
  parenthesized Lisp calls or repeat the subject in every comparison.

#+BEGIN_SRC monad
define ascii-byte? :: Int -> Bool
  byte | >= 0 and <= 0x7f -> True
       | otherwise        -> False
#+END_SRC

  This notation means =byte >= 0 and byte <= 0x7f=.  It is the canonical style
  for range tables, character properties, classifiers, and other unary guarded
  definitions throughout core code. Shared classifications belong in their
  owning module: parser and codec modules import =Data.Char= and compose
  =blank?=, =linebreak?=, =digit?=, and conversion methods instead of defining
  private copies of ASCII tables.

  The same omission applies to unary methods and predicates. Given one =Char=
  subject, write =| blank?= and =| linebreak?= rather than repeating the
  subject. Prefer character literals for readable characters and the public
  type cast for code points whose literal would be visually awkward:

#+BEGIN_SRC monad
define scheme-symbol-character? :: Char -> Bool
  character | blank?      -> False
            | linebreak?  -> False
            | = '('       -> False
            | = ')'       -> False
            | = Char 0x27 -> False
            | otherwise    -> True
#+END_SRC

  In public example code, =Char codepoint= communicates the conversion more
  directly than the lower-level =chr codepoint= helper.

[DEC id:dec.style.multi-subject-relative-guards-2026-08-21 date:2026-08-21 by:human src:user-request conf:high]
  Point-free guard operators fill omitted operands from the clause subjects in
  source order. An explicitly written subject is excluded from that implicit
  set, and the remaining subjects precede the explicit operands. Therefore:

#+BEGIN_SRC monad
define same? :: Int -> Int -> Bool
  left right | = -> True       ; (= left right)
  _ _ -> False

define reversed-same? :: Int -> Int -> Bool
  left right | = left -> True  ; (= right left)
  _ _ -> False
#+END_SRC

  This is one omission rule for unary and multi-subject guards: do not repeat a
  clause subject merely to occupy an operator slot. Retain an explicit infix
  condition when its operand order is clearer to the reader than the compact
  point-free form.

[DEC id:dec.style.receiver-relative-field-guards-2026-08-10 date:2026-08-10 by:human src:user-request conf:high]
  A unary guard may access a field of its sole matched subject with =.field=.
  The dot form is field projection, not closure creation: the reader rewrites
  it to =subject.field= before ordinary guard and infix elaboration. It applies
  only when exactly one guard subject is available; explicit receivers remain
  required for multi-argument clauses.

#+BEGIN_SRC monad
define visible? :: Sample -> Bool
  sample | .xp < 0              -> False
         | .xp >= screen-width  -> False
         | .yp < 0              -> False
         | .yp >= screen-height -> False
         | .luminance <= 0.0    -> False
         | otherwise            -> True
#+END_SRC

[DEC id:dec.style.unconditional-block-arrows-2026-08-10 date:2026-08-10 by:human src:user-request conf:high]
  An unconditional function clause uses an ordinary arrow even when its body
  contains several indented definitions. Never add =| otherwise= merely to
  make the reader recognize a block. The arrow owns every deeper expression,
  and the final expression is the result.

  Multi-argument guarded definitions put their subjects once on a separate
  line, because preserving the complete argument pattern is clearer than
  forcing it beside every branch. Guard bodies use ordinary Wisp application,
  such as =id count= and =null? values=, instead of =(id count)= and
  =(null? values)=. Never repeat the complete multi-argument subject on every
  guarded clause. Use =| otherwise ->= for the fallback branch.

  When two or more consecutive guarded clauses repeat the same pattern, write
  that pattern once as a guard table. This includes constructor patterns such
  as =[c|rest]=; the constructor carries information once, while each aligned
  pipe states a distinct condition. An unguarded final clause with that same
  pattern is semantically exhaustive and is spelled =| otherwise ->=.
  =style/group-repeated-pattern-guards= diagnoses this shape and provides a
  machine-applicable rewrite. A later clause with a different pattern remains
  outside the table and retains its independent matching role.

  Direct indexed selection uses postfix =collection[index]=. The compiler
  resolves it through typed indexing for homogeneous lists, arrays, strings,
  and other indexable collections. Prefer it to =(nth collection index)= when
  selecting one known position. Establish non-emptiness or bounds in an
  earlier guard whenever safety is not otherwise evident.

#+BEGIN_SRC monad
define take :: Int -> [a] -> [a]
  _ []            -> []
  n [x|xs]
      | n > 0     -> (x ++ (take (n - 1) xs))
      | otherwise -> []
#+END_SRC

[DEC id:dec.style.early-return-native-surface-2026-08-21 date:2026-08-21 by:human src:user-request conf:high]
  Put terminating and boundary clauses before the recursive or general clause.
  Bind only values used by that clause: use =_= for a genuinely ignored
  argument, but never discard a value that the guard references. Thus
  =width index | index >= width -> []= is valid and explicit, while
  =_ index | index >= width -> []= is not, because =width= would be unbound.
  For collections, prefer direct shapes such as =[]= and =[x|xs]= over
  recounting the collection to discover whether it is empty.

  Example and library code use public Monad surface forms: string literals for
  characters, =++= for concatenation, postfix indexing, ordinary application,
  patterns, and guards. Do not hide simple source operations behind wrappers
  around =__rt_*= primitives. If the public literal or operator fails, repair
  and regress the compiler or prelude implementation instead of embedding a
  runtime escape hatch in otherwise idiomatic code.

#+BEGIN_SRC monad
define decode-json-value :: Int -> [Int] -> JsonDecode
  offset bytes
    | parser-empty? bytes -> JsonDecodeFailed offset 1
    | bytes[0] = 0x6e     -> decode-json-literal JsonNull ⌜0x6e 0x75 0x6c 0x6c⌝ 10 offset bytes
    | otherwise           ->
        decode-json-integer offset bytes (signed-int offset bytes)
#+END_SRC

[DEC id:dec.style.semantic-values-are-values-2026-08-21 date:2026-08-21 by:human src:user-request conf:high]
  A semantic constant is defined and typed as a value. Never add a dummy
  argument merely to force it into a callback shape:

#+BEGIN_SRC monad
define scm-true :: ScmValue
  ScmBoolean True
#+END_SRC

  When an API genuinely requires a function, keep the value independent and
  give the boundary adapter a name and signature that describe the protocol.
  An ignored parser token is legitimate in an =after-opening= or
  =after-quote= continuation because that function sequences consumed syntax;
  it does not turn the resulting Scheme value into a function.

[DEC id:dec.style.semantic-collection-types-2026-08-21 date:2026-08-21 by:human src:user-request conf:high]
  Collection element types should communicate the collection's domain rather
  than defaulting mechanically to =[Int]=. Use =[Byte]= for encoded octets,
  =[Char]= for characters, and an explicitly scalar-named boundary when the
  current API represents Unicode scalar values as integers. Do not label the
  output of =decode-utf8= as bytes: a scalar such as λ has value 955 and cannot
  inhabit =Byte=. Names such as =scalars= and =scalars->text= preserve that
  distinction until the parser API gains a character-stream abstraction.

  Tutorial modules expose their conceptual shape before their mechanics.
  Organize flagship examples into a few ordered sections, then use short local
  landmarks for dense algorithms. A reader should be able to skim the headings
  and understand the data flow without first reading every helper definition.

[DEC id:dec.style.direct-constructor-cases-2026-08-10 date:2026-08-10 by:human src:user-request conf:high]
  A function must not introduce a parameter and immediately wrap its whole body
  in =match= on that parameter. Put constructor cases in the function clauses.
  For a unary finite or nullary-constructor type, keep the receiver once and
  write aligned constructor pipes:

#+BEGIN_SRC monad
define path-kind-is-regular-file? :: PathKind -> Bool
  kind | RegularFile  -> True
       | Directory    -> False
       | SymbolicLink -> False
       | Other        -> False
#+END_SRC

  Constructor payloads and multi-argument functions use direct patterns in the
  relevant argument position. Keep an explicit =match= when the scrutinee is a
  computed expression, when matching is genuinely nested, or when naming the
  intermediate value improves the procedure.

* Signature-Owned Parameters
:PROPERTIES:

[DEC id:dec.style.signature-owned-parameters-2026-08-10 date:2026-08-10 by:human src:user-request conf:high]
  A named parameter in the type signature is the function parameter. Do not
  repeat it with an arrow before an ordinary body. A docstring may appear
  between the signature and body expression:

#+BEGIN_SRC monad
define abs :: [x : Float] -> Float
  "Return the absolute value of X."
  (if (x < 0.0) (0.0 - x) x)
#+END_SRC

  Equation clauses remain appropriate when the definition performs pattern
  case analysis; the signature-owned form is preferred for one ordinary body.

[DEC id:dec.style.first-class-optionals-2026-08-10 date:2026-08-10 by:human src:user-request conf:high]
  Ordinary zero-or-one results use =T?= and =nil=. A present branch returns the
  value directly; it is promoted into the optional result by the type system.

#+BEGIN_SRC monad
define last :: [a] -> a?
  []     -> nil
  [x]    -> x
  [_|xs] -> last xs
#+END_SRC

  Keep =Maybe= for APIs intentionally exposing its algebraic
  Functor/Applicative/Monad structure. Do not use =Maybe= merely because a
  lookup, search, boundary, or partial observation may have no value.

[DEC id:dec.style.multiline-assembly-2026-08-10 date:2026-08-10 by:human src:user-request conf:high]
  Inline assembly in Core is a detached function-body expression. Put the
  parameter arrow on its own completed line, begin =asm= on the next line,
  and align operands by instruction. Do not compress an assembly program into
  a parenthesized single line.

#+BEGIN_SRC monad
define sys-open :: *U8 -> Int -> Int -foreign-> Int
  path flags mode ->
    asm mov 2     %rax
        mov path  %rdi
        mov flags %rsi
        mov mode  %rdx
        syscall ret
#+END_SRC

  This form is one expression and one assembly program. Continuation lines
  belong to =asm=; they are not additional procedural expressions.

[DEC id:dec.style.large-layout-groups-2026-08-10 date:2026-08-10 by:human src:user-request conf:high]
  Large layouts may group closely related fields horizontally. Keep semantic
  groups on separate lines and align field names and types. This is preferred
  to both a dense undifferentiated wall and unnecessary one-field-per-line
  vertical expansion.

#+BEGIN_SRC monad
layout PosixStatBuffer
  [device           :: Int] [inode          :: Int] [links :: Int] [mode-owner :: Int]
  [group-padding    :: Int] [device-type    :: Int]
  [size             :: Int] [block-size     :: Int] [blocks :: Int]
  [accessed-seconds :: Int] [accessed-nanos :: Int]
  [mtime            :: Int] [mtime-nanos    :: Int]
  [changed-seconds  :: Int] [changed-nanos  :: Int]
  [reserved-a       :: Int] [reserved-b     :: Int] [reserved-c :: Int]
#+END_SRC

[DEC id:dec.style.vertical-layout-fields-2026-08-10 date:2026-08-10 by:human src:user-request conf:high]
  A layout written with one field per line omits square brackets.  The
  indentation already supplies the field boundary, so the unbracketed form is
  the calm canonical spelling for ordinary vertical records.  Square brackets
  remain valid and are useful when two or more related fields share a line, as
  in the large-layout grouping style above.

#+BEGIN_SRC monad
layout ParseResult
  ok     :: Bool
  value  :: Int
  offset :: Int
  error  :: Int
#+END_SRC

[FIX id:fix.style.vertical-layout-arity-boundary-2026-08-10 date:2026-08-10 by:codex src:wisp.c,tests/wisp_unbracketed_layout_fields.mon conf:high]
  Bracketless vertical fields support compound and nominal types, including
  =[TableauEntry]= and =BranchStatus=. Arity prescanning stops at the next
  sibling declaration and leaves that token for the outer scanner; a preceding
  =data= declaration must not absorb a following layout or reinterpret later
  uppercase constructor applications. The regression contains multiple layouts
  and data declarations in one module because the isolated primitive-field case
  was insufficient to expose the boundary bug.

[DEC id:dec.style.arrow-map-literals-2026-08-10 date:2026-08-10 by:human src:user-request conf:high]
  A brace literal containing top-level =key -> value= entries is a map. A
  brace literal without entry arrows remains a set. The reader makes this
  distinction and produces =AST_MAP= before inference; tools must never guess
  map-ness from inferred element shapes.

  The formatter supports three brace-placement policies. They are semantic
  equivalents, and the chosen form is project policy rather than grammar:

#+BEGIN_SRC monad
define compact
{ a -> b
  c -> d }

define hanging
 { a -> b
   c -> d }

define expanded
  {
    a -> b
    c -> d
  }
#+END_SRC

  Formatter configuration also owns the number of blank lines between
  top-level declarations, sections, and related definitions. Defaults must be
  stable; projects may override them through the typed Monad tool-configuration
  module.
[IDEA id:idea.style.self-arrow-2026-08-10 date:2026-08-10 by:laluxx status:deferred]
  In a method context where =Self= is uniquely bound, consider =:->= as exact
  sugar for an initial receiver arrow. Thus =method underscore? :-> Bool=
  elaborates to =method underscore? :: Self -> Bool=, while
  =method lookup :-> Key -> Value= elaborates to
  =method lookup :: Self -> Key -> Value=. Keep the sugar receiver-only and
  reject it at top level or anywhere =Self= is ambiguous. This is a design
  record, not currently accepted syntax.
